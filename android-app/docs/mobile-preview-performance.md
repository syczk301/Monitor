# 4.9.8 手机原画质预览

后续排查与 4.9.12 修复见 [内置接收通道排查记录](embedded-receive-4912.md)：已复现 ZeroTier 固定等待导致的队列积压；Tailscale 真机问题仍需路径证据，未宣称全部修复。

手机首页顶部标题由 `SYNC NET` 改为“实时监控”。

预览使用服务器原始 URL 和原始 JPEG，不添加画质档位参数，不缩放、不重新编码，也不因低帧率或超时降低画质。无需升级电脑端来提供新预览协议。

接收线程完整读取每个 multipart JPEG；解码和绘制分别只保留最新帧，避免慢帧积压。Bitmap 状态在 Canvas 绘制阶段读取，避免每帧重组播放器。FPS 按实际绘制的新画面统计，停流时归零。

内置 Tailscale 与 ZeroTier 使用的本地 CONNECT 转发器将每次转发缓冲从 16 KB 增至 64 KB，减少跨 JNI 的读取次数；本地 TCP 连接启用 TCP_NODELAY，及时送出 TLS 数据。HTTPS 校验、认证和独立连接配置沿用原实现。

调试日志 `MjpegPreview` 每 5 秒记录同一时间窗口的接收、解码、绘制 FPS、接收 Mbps、平均 JPEG 解码耗时及解码失败次数；即使没有新帧到达也会输出，避免停流后缺少诊断。日志不记录服务器地址、认证信息或画面内容。

非全屏底部工具栏（全屏、直播状态、声音）在 3 秒无操作后整体淡出，轻点画面可重新显示或隐藏；操作声音后重新计时。全屏退出按钮也在 3 秒后隐藏，轻点画面恢复，系统返回仍可退出。双击缩放和双指手势保持可用。

诊断只有 1–2 FPS 时：接收 FPS 也低，需要进一步排查服务器出帧和实际网络路径；接收正常而解码低，结合 `decodeMs` 和 `decodeFailures` 排查解码；解码正常而绘制低，再排查 UI/GPU。不能仅凭手机界面 FPS 推断 Tailscale 带宽不足。解码被替换且尚未交给 UI 的 Bitmap 立即回收，减少积压时的内存压力；已经交给绘制线程的 Bitmap 不主动回收。

此前按 1.6 Mbps 限速得到的自动降档测试已经作废，不能据此判断真实手机的 Tailscale 带宽不足。真实手机路径仍需安装新 APK 后复测。

验证：安卓单元测试 28 项、原画质首页界面测试 1 项通过，release 构建、原签名和 16 KB 对齐校验通过。模拟器使用 1280×720、每帧 133,362 字节、30 FPS 的未限速原始 JPEG 流，结果见本次验证记录。该次测试时 4.9.8 APK 尚未发布到 GitHub。

## 真机低帧率复查与 4.9.9 诊断

2026-11-04 用户真机截图为 1.0 FPS / 662 ms，使用内置 Tailscale。手机关闭 FlClash 后用户反馈仍约 1 FPS。

电脑本机 HTTPS 原始流实测 10 秒收到 293 帧（29.29 FPS），1080p，平均约 60 KB/帧，服务器 JPEG 编码约 4.9 ms。电脑到当时在线的手机内置节点 Tailscale ping 为 395/456/406 ms；该节点公网端点的 Windows 出站路由进入 FlClash TUN。进 TUN 本身不能证明被远端代理，还需电脑关闭 TUN 的对照。尝试临时端点直连路由被 Windows 拒绝访问，未修改路由。后续节点离线时无法继续测量。

## 4.9.10 内置接收通道候选修复

用户确认同一手机切换系统网络后帧率正常，故问题范围收敛到内置通道。修正视频客户端与 API/音频共享连接池的耦合：每个视频客户端独立连接池，内置 Tailscale/ZeroTier 的视频固定 HTTP/1.1，避开共享 HTTP/2 socket/流控；系统网络保留原协议列表。Dispatcher 与网络代次校验仍保留，切换网络继续取消旧视频连接。ZeroTier 原生 TCP 在 connect 前启用 TCP_NODELAY，及时发送 TLS 小包。

诊断增加视频协议、累计重连次数和最近异常类型，不输出地址或认证信息。这些是基于已定位接收阶段和代码差异的候选修复；现有证据尚不能证明 HTTP/2 共享或 Nagle 就是真机瓶颈，必须在问题手机内置模式复测。未降低 JPEG 画质，未把内置模式偷偷回退到系统网络，未修改手机身份或网络绑定策略。

4.9.10 验证：34 项单元测试通过（0 失败/错误），release 构建、签名与 16 KB 对齐校验通过。安装包为 dist/monitor-4.9.10-release.apk，GitHub 发布标签为 4.9.10。真机内置通道帧率改善尚未验证。

## 2026-11-12：4.9.11 原生通道复查

用户反馈 4.9.10 的内置 ZeroTier、Tailscale 仍然低帧率。保持已验证的对照：同一手机系统网络及网页版正常。没有接入问题手机的 ADB，本轮以固定 SDK 源码、已打包二进制和 Android 模拟器验证为依据，不将模拟器结果外推为真机已经恢复。

### 查实的缺陷与处理

1. ZeroTier 固定上游 `JavaSockets.cxx` 在 `GetPrimitiveArrayCritical` 与 `ReleasePrimitiveArrayCritical` 之间调用阻塞网络读写。空闲 API keep-alive 和视频读取可能长期占用 Java 数组临界区。已有 ARM64 AAR 的反汇编也确认该调用顺序。JNI 补丁改为先复制到原生缓冲，网络调用结束后只复制实际收到的字节；同时修复 `write_offset` 对 JNI 对象引用本身做地址偏移的问题，并检查数组边界。补丁和源文件校验纳入 SDK 构建脚本。
2. 固定 lwIP 的 `LWIP_NETCONN_FULLDUPLEX=0`，不支持应用原来不同线程对同一 socket 并发读、写、关闭的用法。适配层改为非阻塞调用与短锁串行访问，仅在 EAGAIN 时等待，关闭唤醒等待线程。不会等凑满 64 KB 才转发，也不对每个收到的数据块额外休眠。JNI 原来还从进程全局 `zts_errno` 取错误码，可能被其他连接覆盖；现改为调用返回后立即捕获 Android 线程局部 `errno`，保留 SDK 自身错误码，避免将“暂无数据”误报为 EOF 或把服务未就绪误报为成功。
3. Tailscale 原来只调用 Android 的 `bindProcessToNetwork`，没有设置官方 `netns.SetAndroidBindToNetworkFunc`。Go 的原生 socket 需要逐 FD 绑定；修复通过 `ParcelFileDescriptor.fromFd` 复制描述符、调用 `Network.bindSocket`，关闭复制描述符而保留 Go 所持的描述符。缺少物理网络时返回错误。网卡快照限定当前物理接口与 loopback，避免把未使用的蜂窝接口当作可达端点。网络句柄变化后触发 UDP 重建。
4. 共用 CONNECT 转发器补齐 session 生命周期，处理断开与原生 dial 同时进行的竞态，先关闭本地 socket、再关闭原生连接；诊断不再吞掉原生读取、转发和连接结束的错误类型。

以上问题是代码与打包库层面的实证；尚无证据证明任何一个单独解释了用户手机全部低帧率。系统网络与内置通道也可能走不同外部路径，因此不把此前正常的系统网络结果等同于虚拟网络的带宽测试。

### 新诊断含义

诊断按当前视频 socket 的本地端口关联转发器，不混入 API 或音频连接。原生接收、本地转发、HTTP body 字节和完整 JPEG 分开计数；即使一张 JPEG 尚未收齐，也能看到字节流是否持续前进。等待阶段显示原生读取还是本地转发，异常只显示阶段和类型，不包含地址、认证或画面内容。

原生字节含 TLS 记录开销，HTTP body 含 multipart 头，完整帧仅计 JPEG，三者不要求严格相等。当前通道若在采样窗口内重连，其计数只代表最近连接，结合重连次数判断。读取等待包含正常等下一帧的时间，需与吞吐和帧率一起解读。

### 验证记录

- Android 模拟器物理网络绑定 + HTTPS + 实际本地 CONNECT socket：150 张原始 JPEG，每张 498,002 字节，实测 30.08 FPS；原生计数 74,814,629 字节，HTTP body 74,709,750 字节，JPEG 74,700,300 字节。它验证 Android TLS 与共用转发器，未经过远端 ZeroTier/Tailscale 节点。
- 旧 ZeroTier AAR 的真实 Android 并发测试首个无数据读取即返回 0（EOF），预期为 -11（EAGAIN）。修复后的同一测试完成 50,000 次 EAGAIN 读取和另一 socket 的 50,931 次成功调用，没有错误的 EOF。旧偏移写测试错误返回成功，修复后正确返回负错误码；未据此声称模拟器发生了 native crash。
- 旧、新 AAR 的 3 秒空闲阻塞读取期间，GC 都只用了约 8 ms；本模拟器没有复现 GC 长暂停。JNI critical 区内阻塞仍是需修复的规范问题，但不能把这项测试当作真机 GC 卡顿的证据。
- 修复后 Android 原生回归 8 项通过：JNI GC/偏移/数组边界 3 项、真实原生关闭 1 项、并发 errno 1 项、真实 Go socket 绑定/重新绑定与 FD 所有权 2 项、Android HTTPS 转发 1 项。后一项重测为 30.12 FPS。这些不需要真实账号，不包含问题手机到远端摄像头的完整 overlay 路径。
- 实际画面与控件回归 1 项通过：498,002 字节原始 JPEG、30 FPS，稳态绘制最后 6 次采样平均 29.77 FPS；覆盖非全屏控件自动隐藏、轻点恢复和再次隐藏。
- 全量 JVM 单元测试 48 项通过，Go 单元与真实 tsnet 双节点集成测试通过；release 构建、原签名、16 KB zipalign 校验通过。APK：`dist/monitor-4.9.11-release.apk`，88,142,307 字节，SHA-256：`e22b95c0f01936bf3b967c5b7a612177be10bef66e289e593c5348ea1ada273d`。GitHub 发布标签为 `4.9.11`；问题手机的帧率仍待验证。
