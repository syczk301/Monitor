# 4.9.8 手机原画质预览

手机首页顶部标题由 `SYNC NET` 改为“实时监控”。

预览使用服务器原始 URL 和原始 JPEG，不添加画质档位参数，不缩放、不重新编码，也不因低帧率或超时降低画质。无需升级电脑端来提供新预览协议。

接收线程完整读取每个 multipart JPEG；解码和绘制分别只保留最新帧，避免慢帧积压。Bitmap 状态在 Canvas 绘制阶段读取，避免每帧重组播放器。FPS 按实际绘制的新画面统计，停流时归零。

内置 Tailscale 与 ZeroTier 使用的本地 CONNECT 转发器将每次转发缓冲从 16 KB 增至 64 KB，减少跨 JNI 的读取次数；本地 TCP 连接启用 TCP_NODELAY，及时送出 TLS 数据。HTTPS 校验、认证和独立连接配置沿用原实现。

调试日志 `MjpegPreview` 每 5 秒记录同一时间窗口的接收、解码、绘制 FPS、接收 Mbps、平均 JPEG 解码耗时及解码失败次数；即使没有新帧到达也会输出，避免停流后缺少诊断。日志不记录服务器地址、认证信息或画面内容。

非全屏底部工具栏（全屏、直播状态、声音）在 3 秒无操作后整体淡出，轻点画面可重新显示或隐藏；操作声音后重新计时。全屏退出按钮也在 3 秒后隐藏，轻点画面恢复，系统返回仍可退出。双击缩放和双指手势保持可用。

诊断只有 1–2 FPS 时：接收 FPS 也低，需要进一步排查服务器出帧和实际网络路径；接收正常而解码低，结合 `decodeMs` 和 `decodeFailures` 排查解码；解码正常而绘制低，再排查 UI/GPU。不能仅凭手机界面 FPS 推断 Tailscale 带宽不足。解码被替换且尚未交给 UI 的 Bitmap 立即回收，减少积压时的内存压力；已经交给绘制线程的 Bitmap 不主动回收。

此前按 1.6 Mbps 限速得到的自动降档测试已经作废，不能据此判断真实手机的 Tailscale 带宽不足。真实手机路径仍需安装新 APK 后复测。

验证：安卓单元测试 28 项、原画质首页界面测试 1 项通过，release 构建、原签名和 16 KB 对齐校验通过。模拟器使用 1280×720、每帧 133,362 字节、30 FPS 的未限速原始 JPEG 流，结果见本次验证记录。该次测试时 4.9.8 APK 尚未发布到 GitHub。

## 2026-11-04 复测

28 项单元测试通过；模拟器回归通过，覆盖非全屏工具栏自动隐藏、轻点恢复、再次隐藏及实际绘制 FPS。测试使用本地 HTTPS 原始 1280×720 JPEG（498,002 字节/帧），30 FPS，无限速；接收/解码约 30 FPS，稳态绘制约 28–29 FPS，最后 6 次界面采样均值 28.95 FPS，解码失败 0。此结果仅代表模拟器的系统网络路径，未复现真机 1–2 FPS，不能据此宣称真机问题已解决。

测试同时发现并修复切换配置时主线程清理 TLS 空闲连接导致的 NetworkOnMainThreadException；连接池清理改为后台执行。Release 构建、APK 签名验证和 16 KB zipalign 校验通过。APK 位于 `dist/monitor-4.9.8-release.apk`；GitHub 发布标签为 `4.9.8`。


## 真机低帧率复查与 4.9.9 诊断

2026-11-04 用户真机截图为 1.0 FPS / 662 ms，使用内置 Tailscale。手机关闭 FlClash 后用户反馈仍约 1 FPS。

电脑本机 HTTPS 原始流实测 10 秒收到 293 帧（29.29 FPS），1080p，平均约 60 KB/帧，服务器 JPEG 编码约 4.9 ms。电脑到当时在线的手机内置节点 Tailscale ping 为 395/456/406 ms；该节点公网端点的 Windows 出站路由进入 FlClash TUN。进 TUN 本身不能证明被远端代理，还需电脑关闭 TUN 的对照。尝试临时端点直连路由被 Windows 拒绝访问，未修改路由。后续节点离线时无法继续测量。

4.9.9 在监控页增加可展开的“播放诊断”，每 5 秒显示接收/解码/绘制 FPS、吞吐量、平均解码耗时与失败数，另列服务器预览 FPS。FPS/PING 改为数值与标签上下排列，避免 PING 竖排。此版本不宣称已经修复真机 1 FPS。

更新下载改为 2 MiB 顺序分段；连接中断时在本次下载内从已写入字节续传，最多连续尝试 4 次，等待 1/2/3 秒；对 408/429/500/502/503/504 重试。下载连接等待为 30 秒、无数据读取等待为 60 秒。服务器忽略 Range 时跳过已保存前缀，最终仍校验完整大小、SHA-256、包名、版本和签名。失败退出后仍清理临时文件，不支持跨应用重启续传。

4.9.9 本地构建验证：31 项单元测试通过，含断线后精确续传、临时服务器错误重试、读取超时重试上限；release 构建、签名和 16 KB 对齐校验通过。尚未发布，手机端实际诊断读数和电脑 TUN 对照仍待验证。

追加真机反馈：用户关闭电脑 FlClash TUN 后仍约 1 FPS，该对照未改善，不能将卡顿归因于 FlClash。收到反馈时手机内置节点再次显示离线，且无 ADB 设备，未取得对照期间的接收/解码/绘制数据。下一步采集 4.9.9 手机端播放诊断，避免仅凭延迟猜测瓶颈。


### 12:44 真机播放诊断证据

两张截图：接收/解码/绘制分别均为 0.4 FPS 和 0.6 FPS；完整帧接收吞吐为 0.19 / 0.29 Mbps；平均解码 17.9 / 10.6 ms，解码失败 0；服务器预览 29.0 / 29.3 FPS；请求往返 590 / 690 ms。瓶颈发生在完整视频帧抵达解码器之前，未见解码或绘制额外丢帧。不能把该吞吐量等同于手机物理网络的带宽上限，也不能仅凭离线节点的 Relay 字段证明截图期间经过 DERP。下一步应在同一手机、同一摄像头、同一物理网络下对照另一传输方式，区分内置 Tailscale 路径与共同服务器/网络问题。


### 双通道低帧率与网页版对照

用户反馈内置 ZeroTier 也只有 1–2 FPS，手机使用其他 Wi-Fi；随后反馈网页版正常，网页是否为同手机、同地址待核对。不能再单独归因于 Tailscale 或 FlClash。

共用 ConnectBridge 新增持续流测试：60 帧、64 KiB/帧、8 KiB 分片、30 FPS 定时输入，客户端 CONNECT 后不再发送应用数据；实测 1.946 秒完整收到 60 帧（30.84 FPS），4 项桥接测试通过。此测试使用 JVM 和模拟隧道，不能证明 Android 原生网络 SDK 或真实 Wi-Fi 路径正常。真实服务器本机 HTTP/1.1 实测 29.38 FPS / 14.02 Mbps，HTTP/2 实测 29.33 FPS / 14.05 Mbps，排除服务器仅对 HTTP/2 普遍降速。后续应使用 App 系统网络接入正常网页版相同地址以绕过内置 SDK/CONNECT，并进一步采集实际手机日志。


## 4.9.10 内置接收通道候选修复

用户确认同一手机切换系统网络后帧率正常，故问题范围收敛到内置通道。修正视频客户端与 API/音频共享连接池的耦合：每个视频客户端独立连接池，内置 Tailscale/ZeroTier 的视频固定 HTTP/1.1，避开共享 HTTP/2 socket/流控；系统网络保留原协议列表。Dispatcher 与网络代次校验仍保留，切换网络继续取消旧视频连接。ZeroTier 原生 TCP 在 connect 前启用 TCP_NODELAY，及时发送 TLS 小包。

诊断增加视频协议、累计重连次数和最近异常类型，不输出地址或认证信息。这些是基于已定位接收阶段和代码差异的候选修复；现有证据尚不能证明 HTTP/2 共享或 Nagle 就是真机瓶颈，必须在问题手机内置模式复测。未降低 JPEG 画质，未把内置模式偷偷回退到系统网络，未修改手机身份或网络绑定策略。

4.9.10 验证：34 项单元测试通过（0 失败/错误），release 构建、签名与 16 KB 对齐校验通过。安装包为 dist/monitor-4.9.10-release.apk，GitHub 发布标签为 4.9.10。真机内置通道帧率改善尚未验证。
